# 0002. 린트/타입 강화 옵션의 의도적 비채택

- 상태: 승인
- 날짜: 2026-06-11 (결정 자체는 클린코드 일관성 강제 1차 작업 시점)

## 맥락

클린코드 일관성 강제 작업에서 "더 강하게 걸 수 있는" 옵션들을 검토했고, 일부는 이 리포의
규모·패턴과 맞지 않아 채택하지 않았다. 목록은 `CLAUDE.md` "의도적으로 채택하지 않은 것" 절이
정본이며(에이전트가 매 세션 즉시 봐야 하는 가드레일), 이 ADR 은 근거 상세를 보관한다.

## 결정

다음을 채택하지 않는다.

- **`noUncheckedIndexedAccess`** — 기존 코드가 이미 `??`/`?.` 로 방어적이라 실수 차단 이득이
  작고, 테스트·배열 인덱싱 코드 전반에 `!`/가드 churn 이 크다. 데이터 중심 로직(파서·집계 등)이
  늘면 비용 대비 이득이 역전되므로 재검토.
- **typescript-eslint `strictTypeChecked` 프리셋** — 프리셋의 `no-non-null-assertion` 이 TypeORM
  엔티티/DTO 의 definite assignment `!` 관례(런타임에 ORM/검증이 채움)와 정면 충돌한다. 프리셋
  통째 채택 대신 가치 있는 룰(`no-floating-promises`, `no-unsafe-argument` 등)만 개별 채택했다.
- **복잡도 캡(complexity / max-lines 등)** — 아직 긴 함수/파일 문제가 없다. 문제가 생기면 도입.
- **엔티티/DTO 필드 `!` 제거** — 위와 동일한 이유로 `!` 는 의도적이다. 제거 금지.

## 결과

- 트레이드오프: 타입 안전망 일부를 포기 — 기존 `??`/`?.` 패턴과 코드 리뷰로 보완.
- 재검토 트리거: 데이터 중심 로직 증가(noUncheckedIndexedAccess), 긴 함수/파일 누적(복잡도 캡).
